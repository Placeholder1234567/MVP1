# Local payroll exports

The separate [coverage-log export](coverage-export.md) uses `report.exportCoverage` for bounded CSV/JSON requests, candidates, activity and requester-visible notification evidence. It retains existing notification RLS and labels missing/partial evidence; it does not add coverage to the clinical queue or claim guaranteed delivery.

The supervisor Timesheets screen exports CSV and versioned JSON for the loaded home and period. Exporting re-reads authoritative records through the existing clock aggregation service; a downloaded report may include updates since the screen was loaded. Downloads contain readable staff/home labels and stable references, UTC timestamps, clipped hours, verification/manual/review flags, and the report period. JSON also includes the four aggregation totals. Open clocks contribute zero hours.

Timesheet loads and downloads require an online, visible, unlocked view. Held responses are discarded after account, role, features, home assignments, selected home, privacy or view changes and disposal, including a home change away and back. Account/home/privacy changes clear the loaded report. Offline keeps selected dates and any already loaded same-context report for reading, while refresh and download stay disabled. Export parameters remain those of the loaded report even when the date form changes. This does not alter clock corrections, manual-entry validation, server aggregation or report RLS.

Immediate Care and Timesheets invalidate pending responses when navigation starts, before waiting for the destination page to load or the old component to be destroyed. A cancelled navigation also discards that pending response; another export requires an explicit request.

`report.exportTimesheet` is a POST-only tRPC mutation, requires supervisor/admin plus a reports entitlement and timekeeping, and uses the caller's tenant-scoped transaction and RLS. Every successful export appends a `report_exports` audit event with actor, request details, format and row count; only this insert elevates privileges. It stores no report contents. If auditing fails the export fails. CSV uses the shared spreadsheet formula neutralization helper.

Ranges must be positive and no longer than 366 days. Queries fetch at most 5,001 rows and reject results exceeding 5,000, rather than quietly truncating payroll. Coordinates, client records and manual correction explanations are excluded. The browser creates a temporary object URL for the explicit download and revokes it after use; no report is stored in web storage or a service worker cache. Keep downloaded files in approved agency storage.

Payroll export remains bounded and synchronous; it does not use the queued Care-report workflow or offer a payroll PDF. Care reports have a separate implemented background path, described below. Development work does not provision cloud resources or deploy providers. When offline, export reports a reconnect message and preserves the loaded screen; it does not pretend an incomplete local cache is authoritative payroll.

## Care records

Two paths are implemented: immediate `report.exportClinical` and the account-owned [queued Care reports](queued-care-reports.md) workflow. Queued reports reuse the same clinical rules but permit up to 10,000 CSV/JSON/HTML records or 2,000 PDF records, within 93 agency-calendar days and 8 MB. They use private file storage, a 15-minute generation deadline and 24-hour prepared-file expiry. Refresh and download reauthorize the current account, assigned home and captured person; admins may access agency homes. Downloads require a separate explicit action. The narrower supervisor-home restriction on queued jobs intentionally differs from immediate exports. Local queue timers do not survive restart; expired work needs an explicit new request.

The care-report screen waits for this device's upload queue to be checked and drained before enabling downloads. It also requires an online, visible, unlocked view. A pending response is discarded on account, role, features, home, selected source/person, selected person's current home, privacy, visibility or page-disposal changes, including a home change away and back. Request parameters and completion copy retain the submitted period/format independently of later date edits. A saved local health, attendance, MAR or incident entry refreshes the upload queue before reporting success. This prevents an old "All changes synced" label from allowing a server report before the new record has uploaded. Queue-check failures do not claim completion. The server remains the report source of truth; this guard does not create a local-cache report or guarantee that another device has finished syncing.

`/dashboard/reports` provides a separate bounded clinical export via the POST-only `report.exportClinical` mutation. It requires a supervisor/admin, the `reports` entitlement and the relevant care feature (`charting`, `mar`, `health` or `incidents`). Reports require an authorized home and can narrow to a person currently assigned to that home. Supervisors have the agency-wide home access defined by the existing RLS policies. A foreign home, foreign person or mismatched person/home returns the same scope-unavailable error. All reads and joins remain explicitly tenant-scoped under the caller's RLS transaction; only the append-only export audit insert elevates permissions.

Supported sources:

- Notes: submitted and approved records, optionally approved only; drafts and returned notes excluded. Includes content, author, status, AI indicator, and available signing/resubmission/approval events. Events are the recorded history, not a recreated signature. Imported or offline-created submitted records may have no separate signing event; the report leaves that history empty rather than inventing a signature timestamp. Goal trials and full revision history are not included.
- MAR: every recorded outcome, PRN, acknowledgment, amendment reference and conflict reference. Corrections do not replace originals. Uses medication IDs; current prescription names/doses are omitted because the schema does not snapshot their historical values. This report is not a reconstructed medication order.
- Health: recorded entry data, author reference, flags and acknowledgment.
- Incidents: occurrence time, type, severity, description, action, medical follow-up and review status. Omits precise location, witness/notification contacts and unrelated identity details. Undated incidents are excluded explicitly.
- Attendance: service day, recorded services and recorder identity.
- Goals: recorded trial history linked to signed/approved notes, with an optional approved-only filter, available signature events, trial order, support levels, not-attempted flags/reasons, and grouped progress. Stopped goals remain included. This requires `reports`, `goals` and `charting` entitlements.

From/through dates are inclusive calendar days in the agency's authoritative time zone. Note ranges use the stored shift start day (including overnight notes); MAR uses its stored dose day and attendance its service day. Health and incidents use real timestamp intervals from start midnight through exclusive midnight after the last day, including 23-/25-hour DST days. UTC boundaries and date basis appear in report metadata. Invalid/nonexistent calendar dates are rejected. Changing agency time zone does not rewrite historic stored day keys.

Exports support CSV, versioned JSON, a generated PDF and a script-free UTF-8 HTML document with print styling. HTML escapes every field, blocks external resources and active content with CSP, uses system fonts, and preserves Unicode.

Care PDFs (immediate and account-owned queued) identify the current tenant agency name at generation, read under the caller's transaction and RLS rather than supplied by the browser or captured in session claims. This is a current display label, not the agency's historical name or a new signature. The label is subject to the same font-coverage check and output-size cap as clinical text; an unsupported agency-name glyph also requires CSV or HTML. Existing prepared files remain immutable, so a later rename does not rewrite them. External API PDFs are unchanged; logos, custom branding and scripts outside the bundled font families remain separate work.

The PDF is drawn on the server by `src/lib/server/pdf.ts` (pdfkit with Figtree Regular/SemiBold embedded and subset, Letter size, one labelled block per record, the same values as CSV/HTML except that readings print as "Label: value" lines and signature events one per line rather than as JSON, and a "Confidential care information · Page n of N" footer). No third-party PDF service is used. Figtree remains the default family. When it cannot cover the complete report, the renderer tries bundled SIL-OFL Noto Sans Regular/SemiBold for Greek, Cyrillic and extended Latin (including Vietnamese). Both selected faces must cover every non-whitespace character in all report text before rendering; unsupported scripts such as Ethiopic, CJK and Arabic or emoji still refuse the PDF with a message to use CSV or HTML. The renderer uses one complete family per document rather than partial substitution or transliteration; it never draws blank boxes in place of care-record text. Font bytes and their preserved license/provenance are server-only. This applies to immediate, queued and external API PDFs through the shared renderer, without changing their separate authorization, data or publication rules. The PDF travels to the browser as base64 inside the tRPC response and counts against the 8 MiB limit by its binary size. HTML is an explicit downloaded file, never inserted as active markup in the application. CSV neutralizes spreadsheet formulas. Filenames are generic and contain no client identifiers. DOBs, guardian contacts, addresses, coordinates and complete profile rows are never selected.

Limits are 93 inclusive calendar days, 1,000 source records, 5,000 signature events and 8 MiB serialized output. Queries fetch one sentinel row beyond the cap and reject excessive results; no silent truncation. The HTML/CSV serialized size is checked separately after escaping. Report contents are not stored server-side, cached, logged or written to web storage. Audits retain actor, request details, report type, format and count, plus what the file covered (home, person filter, period, approved-only) and the IDs of the people whose records are in it (staff IDs for timesheets), so a lost download can be traced to the people affected. Never clinical contents. On failure or offline the form stays available with a generic retry message. Keep deliberate downloads in approved storage.

Goal progress uses actual `note_goals` rows joined to their note, client and goal under tenant/RLS constraints. The date basis is the signed note's shift start day; overnight trials retain that day. JSON includes `goalSummary` plus source `rows`; CSV and printable HTML contain separate summary and source-history sections. Percent independent is the rounded count of Independent trials divided by all recorded attempted trials, including Refused (the MVP convention). Not-attempted records are counted separately and excluded from that denominator; inconsistent trials on such a row remain visible in history and are counted as ignored. Empty attempted records and unknown imported codes have explicit counts. Unknown codes remain in the denominator rather than being silently relabeled. No-trial percentages are null, not zero success. The 1,000-row limit applies to source goal records, not summary groups, and the complete summary/history payload remains subject to the 8 MiB limit and export audit.

Goal text/area and stopped timestamp describe the current definition, explicitly labeled as current. The schema has no goal-definition snapshot or versioned trial history; these reports do not reconstruct past wording or trial edits. Only currently submitted/approved notes contribute; drafts/returned notes do not. Goals with no recorded source rows in the period are absent, not reported as failures. Target achievement, missed-day compliance and unobserved support levels are never inferred.

The separate coverage-log increment exports existing requests, candidates, activity and requester-visible notification records with explicit evidence limits. Complete cross-recipient supervisor delivery history remains a source-design target, along with broader PDF glyph/branding support and historical reconstruction where source history exists. Audit metadata CSV already exists through audit.export, and timesheet exports include clock records; do not duplicate those workflows or treat optional intake-report ideas as confirmed missing requirements. An external API capability is not automatically an in-app source, and history absent from original records cannot be reconstructed. Queued care generation/storage delivery is implemented; actual production deployment/provider operation is separate and is not established by this guide.
