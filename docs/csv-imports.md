# Reviewed CSV imports

Open **Reports → Review CSV imports** as a supervisor or administrator. People imports follow the existing person-management role rules; goals require the `goals` feature and medication definitions require `mar`. Existing create APIs and their home/person/tenant checks remain authoritative. This is a bounded import foundation, not an automatic converter for every Therap export.

Download the blank template, convert your source into the exact headers below (any order), and select the file. Unknown or missing columns are rejected; optional values still need their column headers. IDs must match the accessible directory shown on screen. Names are displayed for review, never fuzzily matched.

* People: `home_id,name,first_name,info`. `name` and `home_id` are required; `first_name` and `info` may be blank. DOB, guardians, diagnoses, allergies, behaviors and other health/demographic fields are deliberately not imported by this format.
* Goals: `client_id,area,text,frequency,target`. The person must be active; area/text are required. Steps, start dates, templates and goal scores/trials are excluded.
* Medications: `client_id,name,dose,route,scheduled_times,prn_instructions,notes`. The person must be active and name is required. Use distinct `HH:MM` times separated by semicolons, or as-needed instructions, never both. This creates medication definitions through the normal management API and history/audit flow. It does not administer a dose, create a MAR entry or sign a clinical record. Clinical order review remains necessary.

CSV is UTF-8 comma-delimited, up to 256 KB and 100 nonempty data rows, with at most 16 columns and 4,000 UTF-16 code units per field (individual API fields have smaller limits). A leading BOM, quoted commas/newlines and doubled quotes are supported. Malformed quoting, duplicate/empty headers, NUL and wrong-width rows are rejected or block Apply. Formula-like strings are plain text and are never evaluated. Only the blank header template is downloadable; no preview or error report containing imported records is written to a file.

The raw file, preview, outcomes and returned IDs stay in page memory only. They are not sent to logs, URLs, analytics or browser storage. The selected file is read locally; only explicit reviewed create payloads go to tRPC. Leaving, closing or reloading loses the preview and outcomes, with a warning. Offline preview already on screen remains visible behind normal privacy controls; preparing/applying requires a connection. Privacy locking, a stop request or losing the connection stops subsequent rows after an in-flight request resolves.

All invalid rows block Apply. Duplicate screening checks the file and accessible existing records (including archived/stopped records): people use home + exact normalized name; goals use person + area + text; medications use person + name + dose + route. This deliberately blocks possible duplicates without merging or updating existing records. More than 500 existing goal/medication definitions blocks reliable checking for that person. Checks cannot eliminate concurrent-import races or identify a renamed historical record; review remains required.

Apply is a one-shot, confirmed, sequential batch. It records each created ID and never retries any attempted row in that preview. Requests time out after 20 seconds. A rejected/lost/timed-out response is conservatively **unconfirmed**, because the server may have committed; subsequent rows are not attempted. Earlier successes remain saved—there is no batch rollback. Reconcile unconfirmed/created rows in management before clearing the outcomes or preparing another file. A new upload is not an idempotent replay and can create duplicates after lost responses or changed keys. Do not run simultaneous imports of the same records.

Staff roster imports and actual invitations are deferred. Staff creation can provision Identity Platform accounts and send invitation emails, so it needs a separately reviewed invite/provisioning workflow. The foundation does not claim all four Therap migration categories are complete. No production provider setup, deployment or cloud spending is part of this increment.

Validation includes parser/mapping/batch unit cases and a browser case that uses only unique synthetic records in each browser project, checks invalid-row and offline guards, then imports one person, goal and medication definition through the UI. Local browser launch is intentionally left to the project's approved browser test workflow/CI.
