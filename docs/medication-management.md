# Medication definition management

The medication router now supports create, update, stop and history alongside its existing list operation. Supervisor/admin role and the `mar` entitlement are required for management; services also verify the user's agency and permission. Every query stays explicitly tenant-scoped under the caller's RLS transaction. Creation locks an active person with an assigned home and copies that home for PowerSync. Update and stop lock the medication row so competing operations serialize. A stopped definition cannot be edited, and repeated stopping returns the existing result without another history entry.

Inputs are strict and bounded: name 200 characters, dose 200, route 100, PRN instructions 2,000, notes 4,000 and at most 24 exact HH:mm times. Times are validated, deduplicated and sorted. Optional text can be cleared. As in the MVP, scheduled times and as-needed instructions are mutually exclusive, and as-needed definitions require instructions. Partial updates validate the complete resulting definition, so switching modes must clear the old mode and supply the new one in one request. Unknown/protected fields and empty updates are rejected.

Future starts are rejected because the current daily MAR does not implement delayed activation; retrospective starts remain available. This is an explicit restriction of the specification's optional start timestamp until activation is implemented. The management screen records an existing authorized prescription; it does not prescribe or generate medication instructions.

Each successful mutation appends an actor/action/time medication-history entry in the same transaction. The specification mentions before/after values in medication history, but the schema provides no such columns. Existing immutable audit triggers already retain those values for medication-row changes. The history endpoint exposes its specified timeline, not reconstructed historical prescription wording. No schema change is introduced. Existing MAR rows, amendments and conflicts are never updated by these operations.

Lists and histories fetch a 501st sentinel row and reject more than 500 results rather than silently truncating. Default lists still omit stopped definitions. Dedicated app-router integration cases cover tenant/role/feature checks, inactive people, prescription-mode validation, audit/history, MAR preservation, concurrent stops/edits and result bounds. All fixtures are synthetic; no schema setup or shared data reset is required.
