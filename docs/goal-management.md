# Goal management API increment

The registered `goalRouter` implements the six procedures specified in `.specify/trpc-router.md` goal section: create, update, stop, list, listTemplates and createTemplate. Root registration was added after the concurrent client/administration APIs landed, preserving their registrations. Management UI remains separate while Claude builds the staff, people and setup screens. No client, authentication, navigation or shared spec files are changed.

All procedures require the existing `goals` entitlement. Supervisors/admins create, update and stop goals and manage templates. Caregivers list goals for clients their existing home RLS permits; supervisors retain existing agency-wide visibility. Every query explicitly scopes agency IDs and executes in the caller's RLS transaction. No elevated reads/writes, schema changes, cloud providers or deletion endpoint are introduced. The existing database trigger records mutations in the immutable audit log.

Creation validates and locks an active client, derives home ownership through existing database triggers, defaults omitted start time to now, and accepts the specified historical start timestamp when supplied. Lists default to active goals and can explicitly include stopped goals, including history for archived clients. Definition updates accept only the specified mutable fields; blank frequency/target clears the optional value, and an empty steps list clears steps. Goal/client/agency identity, start/stop timestamps and audit fields cannot be supplied through update.

The specification explicitly says `goal.update` cannot update a stopped goal. Update and stop lock the goal row, and updates also require an unstopped row in the write predicate. Stop is idempotent: repeated requests return the original stop/update times and do not write another audit event. Nothing edits or deletes source `note_goals` records. Definitions edited before stopping remain current definitions, not historical snapshots; trial-history reports continue to label them that way.

Inputs are bounded (area 120, goal text 2,000, at most 30 steps of 1,000 characters, frequency 200 and target 500 characters). Lists fetch one sentinel record beyond a 500-row cap and reject excessive results instead of silently truncating. Template lists can narrow by exact area. Error messages contain no clinical names or goal text.

Templates remain tenant-local, matching the mandatory agency ID and existing RLS. Provisioned `is_default=true` rows are visible only inside their owning agency; this increment creates no global catalog and does not seed defaults. `createTemplate` always writes `is_default=false` and rejects supplied default/agency fields. The service specification mentions createGoalFromTemplate, but no such tRPC endpoint is specified; clients can use returned template text/steps with ordinary validated goal creation. Direct template mutation/deletion and goal-definition version snapshots remain outside this increment.

Application-router tests cover role/plan/home/tenant boundaries, inactive clients, mutation auditing, idempotent stop, stop/update serialization, retained signed trial/export history, default-template ownership and bounded inputs/lists. They use isolated synthetic records in the existing local test database without resetting shared infrastructure.
